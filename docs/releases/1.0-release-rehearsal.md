# AGNARA 1.0.0 RELEASE REHEARSAL

A dry run of the 1.0.0 release from a clean checkout, to find what would fail on
the day before the day arrives. No `1.0.0` was published, no tag was created and
no artifact with a release version left this machine.

```text
CODE READY:          YES
SECURITY READY:      NO
PERFORMANCE READY:   NO
API STABLE:          NO
DOCUMENTATION READY: NO
PUBLICATION READY:   NO
GOVERNANCE READY:    YES
FINAL RELEASE READY: NO
```

`scripts/check_release_readiness.py` reports **40% of mandatory gates**. The
remaining NOs are pending maintainer review rather than pending work. Governance
was the one live configuration gap; #455 applied the reviewed
`.github/rulesets/*.json` definitions to the live branch and tag rulesets on
2026-09-22, and a re-read of the API confirms all three match field for field —
see section 5. The reasoning for each remaining verdict is in section 6.

## 1. `main` / `develop` divergence — resolved

```text
main-only:    2 commits
develop-only: 56 commits
```

The two commits exclusive to `main`:

| Commit | What it is | Action |
| --- | --- | --- |
| `58745f8` | `merge: promote develop's post-A8 state to main (#396)` | Nothing to take. It is the merge that promoted `develop` to `main`; `develop` has since advanced past all of its content. |
| `1c298bf` | `chore(actions): bump the actions group with 3 updates (#427)` | **Integrated.** Real content `develop` lacked. |

A full `git merge origin/main` was attempted first and **abandoned**: because
`main` is 56 commits behind, the merge tried to revert `develop`'s newer work,
conflicting in `idempotency.py`, `telemetry.py` and two test files with `main`'s
older versions. Taking that merge would have silently reverted the idempotency
runtime. The bump was cherry-picked instead, which is the surgical integration
that loses nothing from `develop`.

`develop` was on **older pinned action SHAs** than `main`: `codeql-action`
4.37.9 against 4.38.0, and `setup-uv` 10.0.1 against 10.1.0.

## 2. Findings and fixes

### R-1 — the performance job kept a superseded action pin (low)

`ci.yml` carried both `setup-uv@...20cfd1bf # v10.0.1` and
`...bec219d2 # v10.1.0` after the cherry-pick. The `Performance budgets` job was
added to `develop` after the bump landed on `main`, so dependabot never saw it.
Fixed; one `setup-uv` pin remains in the repository.

### R-2 — two actions were not pinned to a commit SHA (medium)

`.github/workflows/agent-coordination.yml` used `actions/checkout@v7` and
`actions/setup-python@v7`: floating major tags, re-pointable by whoever controls
those repositories, executing on every push to `develop` and `main` and on every
pull request.

It escaped the existing rules because **they are per-file**:
`test_ci_actions_are_pinned_to_exact_versions` reads `ci.yml` and the release
suite reads `release.yml`. `agent-coordination.yml` was covered by neither.

The older rule was also weaker than it looked: it accepted any reference with
two dots, so `@v7.0.1` would have satisfied it, and a tag can be moved whatever
it is called.

Fixed. Both are pinned to SHAs resolved from the GitHub API
(`actions/checkout@v7.0.1` → `3d3c42e5…`, which matches the pin the repository
already trusts elsewhere; `actions/setup-python@v7.0.0` → `5fda3b95…`). A new
gate now requires a 40-character commit SHA for every third-party action in
**every** workflow, plus a trailing comment naming the version, and was
demonstrated to fail when the old reference is restored.

The blast radius was limited by `permissions: contents: read` and the absence of
any secret in that workflow, which is why this is medium rather than high.

### R-3 — a merge silently reverted a release gate's evidence (medium)

`docs/releases/release-status.json` lost the `security-program` detail recorded
by #448. #450 had been branched before #448 merged, so its copy still held the
placeholder text, and merging it restored the placeholder while the threat-model
evidence it described stayed in the tree.

Nothing caught it. The file was valid JSON, every schema and readiness check
passed, and the only thing lost was the sentence saying what had been reviewed.
The readiness report then printed the placeholder — which is how the rehearsal
found it.

Restored, and a new test links each gate to the evidence file it rests on: if
`docs/THREAT_MODEL.md` contains the adversarial-review section, the
`security-program` detail must cite it. Demonstrated to fail on the exact
regression that occurred.

**This is the most important finding in the rehearsal.** The mechanism is
generic: any two concurrent pull requests touching `release-status.json` can
lose a gate's evidence without a conflict, and the release report will quote the
loser.

## 4. Clean-room application

Measured objectively rather than by recollection: across `README.md`, every
`docs/*.md` and `examples/`, 46 runnable Python blocks were extracted and
searched for each feature the 1.0 clean-room rule requires.

| Feature | Runnable example before | After |
| --- | --- | --- |
| capability, DI, policy/principal, direct invocation | yes | yes |
| HTTP, OpenAPI/docs, SSE, MCP, idempotency | yes | yes |
| **telemetry** | **no** | yes — `examples/telemetry.py` |
| **FastAPI embedding** | **no** | yes — `examples/fastapi_embedding.py` |

Nine of eleven were documented. Telemetry and FastAPI embedding were mentioned
in status prose and listed in the generated API reference, but the only worked
code was in `tests/integration/telemetry/` and `tests/integration/fastapi/` — so
an author had to read the test suite, which the clean-room rule counts as a
documentation defect.

Both examples now exist, run outside the checkout, import only governed public
names, and are gated by tests. `examples/telemetry.py` asserts that no payload,
argument value or exception message reaches the exporter.
`examples/fastapi_embedding.py` shows the host owning authentication, lifecycle
and response mapping, the request object stopping at the boundary, and an
unmapped credential being refused rather than executed anonymously.

**Honest limitation.** This is a documentation-coverage audit, not a true clean
room. The same session had already read the internals extensively, so it cannot
claim to have discovered the API from the documentation alone. What is defensible
is the measurement — whether the documentation *contains* a runnable path — and
that is reproducible by re-running the extraction. A genuine clean-room pass
needs someone who has not read this code.

## 5. Governance — closed (#455, 2026-09-22)

Both branches are protected by active rulesets with no bypass actors, and a
third ruleset now makes every `v*` release tag immutable.

| Control | `protect-main` | `protect-develop` | Verdict |
| --- | --- | --- | --- |
| Deletion blocked | yes | yes | good |
| Force push blocked (`non_fast_forward`) | yes | yes | good |
| Pull request required | yes | yes | good |
| Review thread resolution required | yes | yes | good |
| Required status check | `CI` | `CI` | good — one stable aggregate |
| Required approving reviews | 0 | 0 | deliberate, not a gap — see below |
| Require approval of the most recent push | yes | yes | good |
| Strict (branch up to date before merge) | yes | yes | good |
| `protect-release-tags` (`refs/tags/v*`) | active — blocks `update`, `non_fast_forward`, `deletion`; creation unrestricted | | good |

`GIT_WORKFLOW.md` documents `Issue → branch → PR → CI → review → approval →
merge`. `required_approving_review_count` stays `0` deliberately:
`.github/rulesets/README.md` records why — GitHub does not let a pull request
author approve their own pull request, so on a repository with one human
maintainer a required approval could only be satisfied by manufacturing a
review from another account, which is worse than not enforcing it. The review
half of the workflow is therefore a commitment the maintainer keeps and records
in the PR trail, not a platform-enforced control; `2910c5d` (#456) made the
ruleset definitions and the documentation agree on that instead of claiming an
approval nothing enforced.

What changed with #455: `require_last_push_approval` and
`strict_required_status_checks_policy` were live `false` on both branches while
the reviewed definitions in `.github/rulesets/*.json` had already called for
`true` (added by #456). That divergence meant a pull request could merge while
its base had moved — "relying on post-merge CI to discover problems," the same
class of problem as R-3 above — and meant a stale approval on an amended push
would not be re-required. `protect-release-tags` also did not exist live at
all. On 2026-09-22:

- `gh api --method PUT .../rulesets/21973309` (develop) and
  `.../rulesets/21973307` (main) applied `.github/rulesets/protect-develop.json`
  and `protect-main.json`.
- `protect-release-tags` was found already live and active (created
  2026-09-17, id `23602878`) with a payload matching
  `.github/rulesets/protect-release-tags.json` exactly, so no change was
  needed there.
- A fresh `GET` of all three rulesets was diffed field by field against the
  files that produced them; all three match, confirmed from the live
  configuration rather than an exit code.

No ruleset JSON definition changed — they were reviewed and merged in #452 and
#456. No version cut, no release, no tag.

## 9. Supply-chain evidence (V1-37)

Three gaps closed, each of which had produced evidence nobody consumed.

**The digest chain was recorded but never read back.** `build` wrote a
`SHA256SUMS` for the bytes it produced, and no downstream job checked it, so
the digests were a note for a human after the fact rather than a control.
Every one of the nine jobs that downloads the bundle -- including all seven
PyPI uploads -- now re-verifies it before acting.

**The locked dependency audit was an instruction, not a gate.** `SECURITY.md`
has required it since A7 with nothing running it. The `dependency-audit` job
now runs before anything is built, and `build` depends on it.

**There was no SBOM for the Python distributions.** Container images already
carried BuildKit SBOM and max-mode provenance; the wheels and sdists carried
neither.

### What remains unverifiable here

Signing and provenance for published files come from PEP 740 attestations
produced by `pypa/gh-action-pypi-publish` under the workflow's OIDC identity.
Nothing in this repository can prove they were minted, because that requires
an authorized publication. The live Trusted Publisher configuration, the
protected environments' reviewer lists and the attestation shown on PyPI are
all `NEEDS CI` and are recorded that way rather than assumed. `SECURITY.md`
holds the readback procedure for the real release.

No tag, upload, GitHub Release or protected-environment approval occurred in
this task.
