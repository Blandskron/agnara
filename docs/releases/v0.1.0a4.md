# Agnara v0.1.0a4 — Application Alpha

> Draft release notes. Publication, tagging and merging to `main` require the
> owner's explicit authorization.

## What this alpha demonstrates

This experimental alpha demonstrates that Agnara can be consumed as a
framework from outside its source checkout. A clean-room application installed
the candidate wheels as ordinary dependencies and composed direct, HTTP and
MCP capability surfaces using documented public APIs only.

This is application-consumption evidence, not a stable-API, production,
security-certification or interoperability claim. The public API may change
without a deprecation cycle.

## Highlights

- **Seven synchronized distributions:** `agnara`, `agnara-a2a`, `agnara-cli`,
  `agnara-events`, `agnara-http`, `agnara-mcp` and `agnara-telemetry` build at
  one version, and every adapter pins the matching core exactly.
- **Public application composition:** the HTTP and MCP adapters expose
  documented builders over the same frozen capability and exposure model.
- **Governed public API:** every distributable package declares a literal
  public surface, classified in `docs/public-api.json`; repository tooling can
  audit external consumers for private or unclassified imports.
- **Cross-surface consistency:** direct invocation, HTTP and MCP share policy
  ordering, JSON materialization, strict schema validation, canonical failures
  and invocation lifecycle events.
- **Clean-room validation:** an external CPython 3.14 environment installed all
  seven wheels without editable or workspace resolution. Its application used
  no private imports, monkey patches or modified artifacts.
- **Packaging hardening:** the release workflow validates the explicit fourteen
  wheel/sdist artifacts, installed origins, metadata, package data, license
  files and exact first-party dependency constraints before publication.

## Install

After publication, install the core and only the adapters an application uses:

```bash
python -m pip install agnara==0.1.0a4
python -m pip install agnara-http==0.1.0a4 agnara-mcp==0.1.0a4
```

All distributions require CPython 3.14 or newer. The core has no third-party
runtime dependencies. Until the authorized release runs, PyPI continues to
serve `agnara==0.1.0a3` and the six new distribution names are unavailable.

## Migration from v0.1.0a3

Read the complete [a3-to-a4 migration guide](../MIGRATION_a3_to_a4.md). In
particular, applications should:

- use only exports classified in `docs/public-api.json`;
- replace private `_frozen` and `_tracking_id` imports with their documented
  public alternatives;
- use the public `Http` and `Mcp` composition APIs;
- pass JSON transports through the documented materialization boundary while
  preserving strict direct-Python validation; and
- expect declared scopes to execute in the common plan before effects and
  handler invocation.

## Validation

The final engineering audit used candidate commit
`7bd2525d4c68be63fd9f347c7dd3c6de1c847f30`.

- The full suite passed with **3,467 passed and 53 browser tests intentionally
  assigned to the dedicated browser job**.
- Architecture tests passed: **613 passed**.
- Focused cross-surface tests passed: **557 passed** for routing, schemas,
  metadata, HTTP and MCP; **250 passed** for security, policy, failures,
  observability and application composition.
- Exactly seven wheels and seven sdists built at `0.1.0a4.dev0`; archive and
  installed-artifact checks passed for every distribution.
- Ubuntu, macOS and Windows Python 3.14 CI jobs and the required aggregate CI
  job passed on the exact candidate SHA.
- A fresh external application completed thirteen direct/HTTP/MCP, policy,
  failure, introspection and telemetry scenarios; its three clean-room tests
  passed with zero private-import and monkey-patch findings.

The release-readiness record links the reproducible commands and exact-SHA
evidence. Maintainer-only documentation, security and developer-experience
judgments remain separate gates and are never inferred from tests.

## Known limitations

- This remains experimental alpha and does not claim production readiness,
  API stability, free-threading support or benchmark superiority.
- A2A and events remain reserved distributions; distributed tasks, streaming,
  execution identity/idempotency behaviour and interoperability belong to
  later milestones.
- MCP validation is bounded to the pinned SDK and in-process exchanges; it is
  not a claim of complete network-protocol conformance.
- Applications own authentication, identity verification, telemetry providers
  and exporter lifecycle.
- Threat-model and dependency-audit scope, dedicated security static analysis,
  secret-scanning posture, private-reporting readiness and Pending Trusted
  Publisher configuration require explicit owner verification before release.

## Release control

No tag, publication, merge to `main`, version cut or target advance is implied
by this draft. The owner must review the final readiness package, authorize the
release operation and verify the six new PyPI Trusted Publishers. The release
workflow must publish exactly the validated artifact set using OIDC.
