# Agnara v0.1.0a8 — Release Pipeline Recovery

> Candidate release notes. This version is published only by the approved
> `Release to PyPI` workflow run dispatched from `main`; no tag exists until
> that run has passed every gate and a reviewer has approved it. See
> [ADR 0082](../adr/0082-dispatch-driven-release-with-the-tag-as-a-consequence.md).

## What this release is

`0.1.0a8` is release recovery and pipeline hardening after four attempts,
`v0.1.0a4` to `v0.1.0a7`, each consumed a version without publishing the
seven-distribution set. It carries the `0.1.0a7` runtime unchanged: no
framework behaviour, public API or dependency changes. Execution Semantics is
not included; its complete scope moves intact to `0.1.0a9`.

What it changes is how a release happens.

## Why every previous attempt burned a version

The release workflow was triggered by a pushed `v*.*.*` tag. The tag — the
one irreversible act — therefore existed before any gate had run, and a gate
that said no afterwards left an immutable tag naming a release that never
happened. `v0.1.0a5` and `v0.1.0a7` were stopped by publication readiness
*after* being tagged; `v0.1.0a4` and `v0.1.0a6` were rejected by PyPI because
no Pending Trusted Publisher matched the canonical project name `agnara-a2a`.

## The new release flow

A release is a `workflow_dispatch` run of `Release to PyPI` from `main`, with
the version as its only input. The run:

1. re-runs every quality gate, including CodeQL;
2. refuses unless it was dispatched from the current head of `main`, the
   version has no tag anywhere, the workspace and lockfile are synchronized at
   exactly that version, and the `pypi` environment really requires reviewers;
3. builds exactly seven wheels and seven sdists and validates them;
4. installs them in a clean room with the index closed;
5. checks the public index: nothing of this version exists, and the recorded
   publisher kinds match reality;
6. **stops for human approval** in the protected `pypi` environment;
7. only then creates the annotated tag on the approved commit;
8. publishes `agnara-a2a`, `agnara-cli`, `agnara-events`, `agnara-http`,
   `agnara-mcp`, `agnara-telemetry` and finally `agnara`, one step each, with
   attestations and metadata verification and without `skip-existing`;
9. verifies that all seven carry a wheel and an sdist and installs the
   published set;
10. creates the GitHub Release only after that verification passed.

Nobody runs `git tag` any more.

## Exact PyPI configuration

Each active or Pending Trusted Publisher must use provider **GitHub Actions**,
owner `Blandskron`, repository `agnara`, workflow `release.yml`, environment
`pypi`. Its Project name must be exactly the corresponding value:

- `agnara` (active publisher, in the project's own Publishing settings)
- `agnara-a2a` (pending)
- `agnara-cli` (pending)
- `agnara-events` (pending)
- `agnara-http` (pending)
- `agnara-mcp` (pending)
- `agnara-telemetry` (pending)

`agnara_a2a` is the wheel and sdist filename normalization, never the project
name. `docs/releases/publication.json` records the readback of each; it must
be dated on or after the `0.1.0a6` failure, be signed by a human account, and
is refused otherwise.

## Owner checklist

1. Read back all seven publishers on PyPI and record them in
   `publication.json` with `status: VERIFIED`.
2. Give the `pypi` GitHub environment at least one required reviewer and
   restrict its deployment branches to `main`.
3. Dispatch `Release to PyPI` from `main` with version `0.1.0a8`.
4. Approve the run twice when asked: once to create the tag, once to publish.
