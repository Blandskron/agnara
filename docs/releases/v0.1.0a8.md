# Agnara v0.1.0a8 — Release Pipeline Recovery

> Candidate release notes. This version is published only by the approved
> `Release to PyPI` workflow run dispatched from `main`; no tag exists until
> that run has passed every gate and a reviewer has approved it. See
> [ADR 0082](../adr/0082-dispatch-driven-release-with-the-tag-as-a-consequence.md).

## What this release is

`0.1.0a8` is release recovery and pipeline hardening after four attempts,
`v0.1.0a4` to `v0.1.0a7`, each consumed a version without publishing the
seven-distribution set. It carries the `0.1.0a7` runtime unchanged: no
framework behaviour, public API or dependency changes. Execution Semantics is
not included; its complete scope moves intact to `0.1.0a9`.

What it changes is how a release happens.

## Why every previous attempt burned a version

The release workflow was triggered by a pushed `v*.*.*` tag. The tag — the
one irreversible act — therefore existed before any gate had run, and a gate
that said no afterwards left an immutable tag naming a release that never
happened. `v0.1.0a5` and `v0.1.0a7` were stopped by publication readiness
*after* being tagged; `v0.1.0a4` and `v0.1.0a6` were rejected by PyPI because
no Pending Trusted Publisher matched the canonical project name `agnara-a2a`.

## The new release flow

A release is a `workflow_dispatch` run of `Release to PyPI` from `main`, with
two inputs: the version and the **phase**. PyPI allows at most three Pending
Trusted Publishers at a time, so `0.1.0a8` is published in three dispatches:

| Phase | Publishes | Verifies on PyPI | Tag / Release |
| --- | --- | --- | --- |
| `bootstrap-1` | `agnara-a2a`, `agnara-cli`, `agnara-events` | those three, wheel + sdist | none |
| `bootstrap-2` | `agnara-http`, `agnara-mcp`, `agnara-telemetry` | the six adapters | none |
| `final` | `agnara` | all seven, wheel + sdist, then a clean install | `v0.1.0a8`, then the GitHub Release |

Every dispatch:

1. re-runs every quality gate, including CodeQL;
2. refuses unless it was dispatched from the current head of `main`, the
   version has no tag anywhere, the workspace and lockfile are synchronized at
   exactly that version, and the `pypi` environment really requires reviewers;
3. builds exactly seven wheels and seven sdists and validates them;
4. installs them in a clean room with the index closed;
5. checks the public index for the phase: earlier phases are complete, this
   phase and later ones carry no file of the version, and the recorded
   publisher kinds match reality;
6. **stops for human approval** in the protected `pypi` environment;
7. publishes only this phase's projects, one job and one OIDC identity each,
   with attestations and metadata verification and without `skip-existing`;
8. verifies that everything published so far carries a wheel and an sdist.

Only the `final` phase then creates the annotated tag on the dispatched commit
and the GitHub Release, after all seven are verified. If an upload or a
verification fails in any phase, no tag exists. Nobody runs `git tag` any more.

## Exact PyPI configuration

All publishers use GitHub Actions, owner `Blandskron`, repository `agnara`,
workflow `release.yml`, with these distinct bootstrap environments:

| Project | Bootstrap environment |
| --- | --- |
| `agnara` | `pypi-core` |
| `agnara-a2a` | `pypi-a2a` |
| `agnara-cli` | `pypi-cli` |
| `agnara-events` | `pypi-events` |
| `agnara-http` | `pypi-http` |
| `agnara-mcp` | `pypi-mcp` |
| `agnara-telemetry` | `pypi-telemetry` |

`agnara_a2a` is the wheel and sdist filename normalization, never the project
name. `docs/releases/publication.json` records the readback of each; it must
be dated on or after the `0.1.0a6` failure, be signed by a human account, and
is refused otherwise.

## Owner checklist

1. Give the `pypi` GitHub environment at least one required reviewer and
   restrict its deployment branches to `main`. Restrict every bootstrap
   environment to `main` too, with no secrets. See ADR 0083.
2. `bootstrap-1`: the pending publishers `agnara-a2a`, `agnara-cli` and
   `agnara-events` are read back and recorded `VERIFIED` in
   `publication.json`. Dispatch `Release to PyPI` from `main` with version
   `0.1.0a8` and phase `bootstrap-1`; approve once when asked.
3. `bootstrap-2`: with three pending slots free again, create the pending
   publishers `agnara-http`, `agnara-mcp` and `agnara-telemetry`, read them
   back, record them `VERIFIED`, merge that record, then dispatch phase
   `bootstrap-2` and approve once.
4. `final`: read back the active `agnara` publisher (`pypi-core`), record it
   `VERIFIED`, merge, dispatch phase `final` and approve once. Verification of
   all seven, the tag and the GitHub Release follow in that order.

# Agnara v0.1.0a8 — Publication Baseline

`0.1.0a8` is the retained proof that Agnara can publish its complete,
synchronized distribution set through a reviewed workflow. It is not a
supported product baseline and does not establish a compatibility promise.

The workflow dispatches from `main`, rebuilds and verifies all distributions,
waits for approval in the protected publishing environment, and creates the
tag only after successful publication verification. Distinct publisher
environments allow the workflow to publish the complete set safely.

Future publication uses this workflow for the first product release, `1.0.0`.
See ADR 0082 and `docs/MAINTAINERS_RELEASE.md` for the operational contract.
