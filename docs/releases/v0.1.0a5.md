# Agnara v0.1.0a5 — Publication Recovery

> Draft release notes. Tagging, publication and merging to `main` require the
> owner's explicit authorization, and this release additionally requires the
> PyPI Trusted Publisher confirmations recorded in
> [`publication.json`](publication.json).

## What this release is

`0.1.0a5` publishes what `0.1.0a4` was supposed to publish, and fixes the
release system that did not.

It carries the `0.1.0a4` implementation **unchanged** — no runtime source file
differs between the two — so everything the [`0.1.0a4` notes](v0.1.0a4.md)
describe about the framework is what you get here. What changed is the pipeline
around it.

If you installed `agnara==0.1.0a4`, upgrade. That version's adapters were never
published and never will be.

## What happened to 0.1.0a4

`v0.1.0a4` was tagged on reviewed `main` history. Its release run passed the
full CI matrix, both CodeQL languages, the lockfile gate, the build of all
fourteen artifacts, artifact metadata and content validation, and a clean-room
install of all seven wheels with the index closed.

Then it published one file.

| Step | Result |
| --- | --- |
| `agnara-0.1.0a4-py3-none-any.whl` | `200 OK` |
| `agnara_a2a-0.1.0a4-py3-none-any.whl` | `400 Non-user identities cannot create new projects` |
| everything after it | never attempted |

`twine` uploads every wheel before any sdist and stops on the first failure, so
the `agnara` sdist and all twelve sibling artifacts were never uploaded.
Post-release verification and the GitHub Release were later *steps of the same
job*, so both were skipped. Run
[34285830444](https://github.com/Blandskron/agnara/actions/runs/34285830444)
holds the log.

The `400` is what PyPI answers when the authenticated OIDC identity has no
pending Trusted Publisher matching the uploaded project name. The six new PyPI
projects did not exist, and nothing in the repository was responsible for
knowing that before the upload started.

**State left behind on PyPI:** `agnara 0.1.0a4` exists as a wheel with no sdist;
`agnara-a2a`, `agnara-cli`, `agnara-events`, `agnara-http`, `agnara-mcp` and
`agnara-telemetry` do not exist as projects at all.

`v0.1.0a4`, its commit and the uploaded file are historical and are not
modified, moved or replaced. ADR 0078 records why the recovery is a new
pre-release rather than a moved tag, a `.post1` or a rebuilt artifact.

## What changed in the release system

Full reasoning in [ADR 0079](../adr/0079-sequenced-publication-and-publish-readiness.md).

- **PUBLISH READY is now a separate claim from CODE READY.**
  `scripts/check_publication_readiness.py` owns everything between a correct
  commit and seven complete distributions on an index. `0.1.0a4` satisfied
  every gate the repository had and none of them was this one.

- **The registry contract is a reviewed file.**
  [`docs/releases/publication.json`](publication.json) records, per project and
  per target version, that a human read the Trusted Publisher tuple back from
  PyPI. Anything not `VERIFIED` for the exact target fails readiness and the
  workflow refuses to upload. The same requirement existed for `0.1.0a4` — as a
  paragraph.

- **The kernel is published last.** Siblings first, `agnara` last. An adapter
  pins its kernel exactly, so a partial publication now fails *closed*: nothing
  new resolves and the published `agnara` version does not move. `0.1.0a4`
  failed open.

- **Each distribution is uploaded in its own step**, so a failure names a
  distribution rather than a position in a fourteen-file batch.

- **Publication, verification and announcement are separate jobs**, chained by
  real `needs`. A successful GitHub Release can no longer coexist with an
  incomplete PyPI.

- **Verification checks completeness, not installability.** Every distribution
  must carry both a wheel and an sdist at the released version. `agnara 0.1.0a4`
  would fail this today.

- **`skip-existing` stays off.** A file that already exists at the version being
  published means something has gone wrong, and suppressing it would make a
  rerun look like a success.

- **One source of truth for the seven names.**
  [`docs/distributions.json`](../distributions.json) declares the reviewed set;
  the scripts, the architecture tests and both workflows read it instead of
  keeping five independent copies. Canonical project names stay
  dash-separated — `agnara_a2a-0.1.0a5.tar.gz` is PEP 427/625 filename
  normalization, not a naming defect.

- **Supply chain.** Every third-party action on the publication path is pinned
  to a full commit SHA with the human version in a trailing comment, and
  `.github/dependabot.yml` keeps those pins moving. `contents: write` moved off
  the publishing job. The artifact bundle is retained for thirty days instead of
  one, because diagnosing a partial publication needs the exact bundle.

## Install

```bash
python -m pip install "agnara==0.1.0a5"
python -m pip install "agnara-http==0.1.0a5" "agnara-mcp==0.1.0a5"
```

All distributions require CPython 3.14 or newer. The core has no third-party
runtime dependencies. Adapters pin the exact matching core, so upgrade the ones
you use together.

## Migration from 0.1.0a4

None. The implementation is identical. If you are coming from `0.1.0a3`, the
[a3-to-a4 migration guide](v0.1.0a4.md#migration-guide) is the one that applies,
with `0.1.0a5` substituted for `0.1.0a4` in every version pin.

## Validation

Recorded per gate, with the commands and their exact results, in
[`release-status.json`](release-status.json).

What could **not** be validated from this repository, and must not be inferred:

- **PyPI Trusted Publisher configuration.** No check running here can observe
  PyPI's publisher table. This is a mandatory manual gate and the reason
  `publication.json` exists.
- **The `pypi` GitHub Environment protection policy.** An owner decision; it
  currently has no protection rule and allows administrator bypass.
- **The publish, verify and release jobs end to end.** They cannot run without
  publishing. Their structure — that the GitHub Release depends on verification
  which depends on publication — is asserted by the test suite against the
  workflow file rather than demonstrated by a run.

## Known limitations

Unchanged from `0.1.0a4`: experimental alpha, no API-stability, production or
free-threading claim; A2A and events remain reserved distributions with no
runtime; MCP validation is bounded to the pinned SDK; applications own
authentication, telemetry providers and exporter lifecycle.

Additionally:

- `agnara 0.1.0a4` remains resolvable on PyPI until it is yanked. The
  recommended reason is `Partial multi-distribution publication; superseded by
  0.1.0a5.` A yank keeps the file available to anyone who already pinned it and
  removes it from ordinary resolution. Deletion is not recommended and not
  performed.
- Six sibling projects will be created by their pending publishers on first
  upload. Until that upload succeeds they do not exist, and no readback of a
  404 proves a pending publisher is configured.

## Release control

No tag, publication or merge to `main` is implied by this draft.
`release-status.json` stays `IN_PROGRESS` while any mandatory gate is pending,
and `--require-ready` must keep failing while `pypi-trusted-publishers` is
`NEEDS_REVIEW`.

### Owner gates

All eight are `NEEDS_REVIEW`. These are recommendations, not approvals, and the
readiness tool never satisfies a manual gate itself.

| Gate | Basis | Recommendation |
| --- | --- | --- |
| Every PyPI Trusted Publisher is confirmed for this exact target | Nothing here can observe PyPI. The index readback shows `agnara` without `0.1.0a5` and six 404s, which proves nothing about publisher configuration. | **No recommendation possible.** The owner must observe it. |
| Security and release checks | `pip-audit` 2.10.1 found no known vulnerabilities across 30 locked third-party runtime dependencies; 38 security tests pass; the publication path is SHA-pinned and `contents: write` is off the publishing job. CodeQL runs on the PR. The `pypi` environment still has no protection policy. | ACCEPT for this bounded alpha, after choosing the environment policy |
| Documentation reflects implementation | No runtime source changed; the documentation change is the release system and the incident record. Documented examples still execute. | ACCEPT |
| Public API is sufficient | Unchanged from `0.1.0a4`. | ACCEPT |
| DI works naturally | Unchanged from `0.1.0a4`. | ACCEPT |
| Capabilities declared cleanly | Unchanged from `0.1.0a4`. | ACCEPT |
| CLI and introspection help | Unchanged, and the installed console script was re-exercised at `0.1.0a5`. | ACCEPT |
| Documentation reproduces applications | Unchanged from `0.1.0a4`. | ACCEPT |

### Owner checklist before tagging

1. At <https://pypi.org/manage/account/publishing/>, add a pending publisher for
   each of `agnara-a2a`, `agnara-cli`, `agnara-events`, `agnara-http`,
   `agnara-mcp`, `agnara-telemetry` — owner `Blandskron`, repository `agnara`,
   workflow `release.yml`, environment `pypi`.
2. On the existing `agnara` project, read the same four fields back.
3. Check <https://pypi.org/manage/projects/> for a project created under a
   misspelled name. The `0.1.0a4` upload was refused, so it created nothing, but
   a publisher registered under the wrong name may still exist. Delete the wrong
   project if one is there, remove the wrong publisher, and re-register using
   the exact canonical name. Do not rename anything in this repository to match
   a registry typo.
4. Record each confirmation in `docs/releases/publication.json` and commit it.
5. Choose the `pypi` environment protection policy.
6. Re-run `uv run python scripts/check_publication_readiness.py --version 0.1.0a5 --online`.
7. Only then merge, tag and push `v0.1.0a5`.
