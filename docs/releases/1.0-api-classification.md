# 1.0.0 public API classification — evidence and proposal

`docs/PUBLIC_API.md` requires that a `stable` classification "requires an
explicit `1.0.0` decision supported by release evidence", and the
`stable-public-api` release gate requires a maintainer to approve the
compatibility commitment. This document is that evidence and a proposal. It
does not promote anything; `docs/public-api.json` is unchanged and every export
remains `provisional`.

## What the surface actually is

Measured from `docs/public-api.json`, verified against each module's live
`__all__` (they agree exactly, 0 mismatches):

| Figure | Value |
| --- | --- |
| Classified export entries | 337 |
| Governed modules | 49 |
| **Distinct names** | **166** |
| Entries that are an alias for a name reachable at a shallower path | 171 |
| Governed modules whose every export is such an alias | 36 of 49 |

The headline number has been quoted three different ways across the
documentation — 292, 324 and 337 — because nothing said whether it counted
names or import paths. It counts paths. A name reachable from `agnara`,
`agnara.capability` and `agnara.capability.identity` is classified three times.

## The decision this forces

**Promising all 337 entries promises three import spellings per name for the
whole of `1.x`.** Every alias path becomes a compatibility obligation, and
moving a leaf module later becomes a major release.

The 13 modules that contribute at least one canonical path:

| Module | Canonical names |
| --- | --- |
| `agnara` | 41 |
| `agnara.execution` | 32 |
| `agnara.introspection` | 23 |
| `agnara_mcp` | 20 |
| `agnara_http` | 14 |
| `agnara.schema` | 13 |
| `agnara.core.di` | 9 |
| `agnara.exposure` | 7 |
| `agnara_cli` | 4 |
| `agnara_telemetry` | 2 |
| `agnara.policy` | 1 |

The other 36 modules — `agnara.capability.identity`, `agnara.execution.result`,
`agnara.policy.base`, `agnara_http.composition`, `agnara_mcp.tools` and the
rest — contribute no name that is not already reachable higher up.

### Proposal 1: promise names at their canonical path, not every path

Classify the 166 canonical paths `stable` and leave the 171 alias paths
unpromised. The aliases keep working; they simply are not a commitment, so a
leaf module can be split or renamed in a minor release as long as the canonical
import is unaffected.

This is the single highest-leverage decision available before 1.0. It cuts the
promised surface by roughly half without removing anything an application uses.

The counter-argument, which a maintainer should weigh: an application that today
imports `from agnara.execution.result import Success` is relying on an alias. It
would keep working, but without a promise. If that spelling is considered
already-endorsed in the wild, the alias set has to be promised too.

## Named questions from the 1.0 scope

### `agnara.core.di` — the spelling should change

Nine names (`DIContainer`, `DIRegistry`, `Scope`, `provider`, `compile_dag`,
`ProviderDefinition`, `ProviderType`, `DependencyCycleError`,
`DependencyResolutionError`) are reachable **only** at `agnara.core.di`.

`core` reads as an internal package everywhere else in Python, and this is the
only place the public surface uses it. An application writing
`from agnara.core.di import provider` is being told, by the path, that it is
reaching into internals — while it is in fact using the intended dependency
injection API.

Proposed: re-export the nine names at `agnara.di` before 1.0 and make that the
canonical path, keeping `agnara.core.di` as an unpromised alias. Renaming after
1.0 costs a major release; renaming now costs a changelog entry.

### Exports with no direct test coverage

Five distinct names are not referenced by any test:

| Name | Canonical path |
| --- | --- |
| `JsonSchema` | `agnara.schema` |
| `IdempotencyConflictError` | `agnara.execution` |
| `IdempotencyInProgressError` | `agnara.execution` |
| `VisibilityRule` | `agnara.introspection` |
| `McpPrincipalMapper` | `agnara_mcp` |

`docs/PUBLIC_API.md` criteria require a stable API to be covered by tests. These
are the only five that are not. Each is a protocol or alias type rather than
behaviour, which is a plausible reason but not an automatic exemption: the two
idempotency errors in particular are raised by the runtime and can reach an
application.

Proposed: add direct tests for the five, or classify them deliberately as not
stable. Do not promote them on the assumption that a type alias cannot break.

### Documentation coverage

All 337 entries appear somewhere in the documentation corpus, so the "appears in
public documentation" criterion is met across the board and excludes nothing.

## What this document does not do

It does not decide. Every export is still `provisional` in the manifest, and no
status anywhere has been changed to `stable`. It does not rename
`agnara.core.di`, does not add the five missing tests, and does not remove any
alias path; each of those is a separate reviewed change, and the first two are
pre-1.0 breaks that need their own changelog entries under ADR 0021.

It also does not review all 166 names individually for naming quality or
behavioural fitness. The structural questions above dominate: deciding the path
policy changes what half the surface means, and is worth settling before
anyone spends time on a symbol-by-symbol pass.
