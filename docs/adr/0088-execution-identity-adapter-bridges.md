# ADR 0088 — Execution Identity Across Adapter Boundaries

- Status: Accepted
- Date: 2026-09-13
- Tracking: GitHub Issue #390
- Initiative: I3
- Amends: ADR 0087 D3
- Related: ADR 0023, ADR 0054, ADR 0055, ADR 0087, RFC 0008

## Context

ADR 0087 made `execution_id` runtime-owned, but did not specify how the two
implemented adapters observe it. Treating an HTTP request id or an MCP
JSON-RPC request id as execution identity would let a caller choose a value
that looks like an idempotency or authorization proof. Hiding every generated
identity, conversely, prevents operators from correlating an HTTP result with
its invocation span.

## Decision

`execution_id` remains generated by `ExecutionContext`; no HTTP or MCP input,
metadata field, principal, session, request id, trace context or tracking id
can supply or replace it. `invocation_id` remains a separate, per-attempt
telemetry identity. Neither identifier grants authority, selects an
idempotency record, authorizes a retry, or proves request equivalence.

HTTP accepts at most one ASCII opaque `X-Request-ID` of at most 128 characters
as untrusted `tracking_id`. A duplicate or malformed value is a redacted 400
before an execution begins. It is never emitted to OpenTelemetry. Once an HTTP
execution exists, every complete result and SSE response carries its generated
`agnara-execution-id` response header, including canonical failures; routing
and binding failures carry none.

MCP may copy a syntactically valid, bounded JSON-RPC request id into the same
untrusted `tracking_id` slot. Invalid request ids remain valid MCP framing but
are dropped from Agnara correlation. MCP adds no result-field extension; the
generated identity is observable through the runtime events and tracing bridge.

The OpenTelemetry tracing bridge writes `agnara.execution.id` and
`agnara.invocation.id` only on spans. Metrics retain their low-cardinality
attributes and neither tracing nor metrics exports tracking IDs, principals,
payloads, fingerprints, credentials, or raw transport metadata.

## Threat and concurrency analysis

Request identifiers are attacker-controlled at a public adapter boundary.
Validation bounds the value that can reach in-process lifecycle hooks, and no
caller value is promoted into execution identity. Opaque generated identifiers
contain no principal, capability topology, or payload. Per-context creation and
the tracing hook's lock retain isolation for concurrent HTTP/MCP calls; no
global execution registry or adapter state is introduced.

## Consequences

- Direct invocation, HTTP, and MCP retain the same generated execution-identity
  semantics.
- Hosts may bridge their request identifiers as correlation only; RFC 0008
  still owns a future general embedded-host contract.
- Idempotency storage, replay, retries, durable execution and protocol task
  resumption remain outside this decision.
