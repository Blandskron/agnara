# ADR 0087 — Execution Identity Before Operational Idempotency

- Status: Accepted
- Date: 2026-09-13
- Tracking: GitHub Issue #386
- Initiative: I3
- Related: ADR 0023, ADR 0084, ADR 0085, RFC 0001

## Context

The runtime currently generates an `invocation_id` solely to pair telemetry
start and terminal events. Capability identity is stable, `tracking_id` is
optional correlation, and idempotency is declaration metadata. None is an
operational identity that can safely scope deduplication or later durable work.
Transport request IDs, SSE event IDs, MCP sessions and caller metadata are not
interchangeable with that missing identity.

## Decision

### D1 — One opaque execution identity scopes one logical attempt

The future execution boundary receives an immutable, protocol-neutral
`execution_id`: a non-empty, ASCII opaque token generated by the framework
with at least 128 bits of randomness when the caller did not present an
accepted idempotency key. It is unique within the application deployment's
idempotency-store namespace; it is neither a capability id nor a transport
request id and is not inferred from headers, sessions, SSE `id`, MCP task ids,
or telemetry correlation.

`invocation_id` remains an ephemeral telemetry pairing id. One execution may
produce several invocations only when a later governed mechanism explicitly
reuses a completed result; every actual handler attempt still gets its own
`invocation_id`. `tracking_id` remains observability-only and never selects or
merges executions.

### D2 — Idempotency keys are untrusted selectors, not identities

An adapter may pass a caller-supplied idempotency key only through an explicit
future boundary. The store scopes it by at least capability id and authenticated
principal/tenant authority, validates length and syntax before lookup, and
binds it to a canonical request fingerprint. A mismatch, cross-capability use
or cross-principal reuse is rejected; a key never authorizes a retry or grants
access. The store records the generated `execution_id` and its outcome, rather
than treating the key itself as a public execution identifier.

### D3 — This record decides no durable runtime

This decision adds no storage, replay, scheduler, task, persistence, automatic
retry, HTTP header, MCP field or public API. A later I3 record defines store
claims, TTL, in-flight races, failure retention and result reuse. Transport
projections may expose only that later accepted behavior.

## Threat and concurrency analysis

Caller keys, request ids and correlation metadata are attacker-controlled.
Opaque runtime identity prevents cross-capability confusion and avoids leaking
principal or payload data into an identifier. Store operations must be atomic:
two matching keys cannot execute effects twice. Store records and telemetry
must redact keys and fingerprints. Random collisions fail closed rather than
merging executions.

## Consequences

- I3 has a stable domain for operational idempotency without rebranding an
  existing telemetry or transport value.
- Existing behavior is unchanged; idempotency remains metadata until the store
  and runtime are implemented with race and TTL evidence.
- Durable execution, scheduling, retries and protocol resumption remain out of
  scope.

## Alternatives rejected

**Reuse `invocation_id`.** It is per handler attempt and deliberately absent
without observers. **Use a transport request id.** It is spoofable,
transport-local and may be absent. **Let a key be global.** It enables
cross-capability and cross-principal confusion.
